# Nursing School Pinkprint

Flashcards, practice quizzes and study guides for nursing students (NUR 114, then NUR 121), drafted from ATI and lecture material.

- Live site: https://nursingschoolpinkprint.com
- Repo: `nemxcvi/nursingschoolpinkprint`
- Plain static HTML/CSS/JS in `nursing-study-site/`. No build step, no package manager, no tests.

## Hosting and deploys

- Hosted on **Cloudflare Pages**, project **`nursingschoolprep`**, connected to this GitHub repo. The site root is `nursing-study-site/`.
- `main` deploys to production (nursingschoolpinkprint.com).
- Every other branch gets a preview deploy at `https://<branch-alias>.nursingschoolprep.pages.dev/`. The alias is the branch name lowercased, with anything that isn't a letter or number turned into `-`. Cloudflare shortens long aliases, so keep branch names short, e.g. `preview-study-guide-and-nav` → https://preview-study-guide-and-nav.nursingschoolprep.pages.dev/.
- The Cloudflare tools in Claude sessions can't list or trigger Pages builds, so build status is checked in the Cloudflare dashboard (Workers & Pages → nursingschoolprep → Deployments).

## How to ship a change (always follow this)

1. Work on a short preview branch (e.g. `preview-<topic>`). If the session assigned a branch, use that one.
2. Push it and give the owner the preview link: `https://<branch-alias>.nursingschoolprep.pages.dev/`.
3. **Wait for explicit approval.** Never push to `main` before the owner OKs the preview.
4. After approval, fast-forward or merge the branch into `main` and push. That deploys to production.

## Site structure

- `nursing-study-site/assets/site-data.js` is the single source of truth for courses, units, widgets and search. Adding a page means adding it here too.
- Units live in `nursing-study-site/unit-N-<slug>/`, each with an `index.html` plus flashcard, quiz and study-guide pages.
- Shared code and styles are in `nursing-study-site/assets/` (`style.css`, `header.js`, `flashcards.js`, `practice-quiz.js`, `quiz.js`, `theme.js`, `unit-filter.js`). Pages load them with `?v=N` cache-busters. When you change a shared file, bump its `?v=` number on **every** page that loads it.
- Themes: light/dark plus pink/blue palettes, stored in `localStorage` (see the inline script in each page's `<head>`).

## Link previews (iMessage, GroupMe, etc.)

- Every page repeats the same meta block: `description`, `og:*` and `twitter:*`. The tagline, kept identical to the text in the image, is:
  `Flashcards, quizzes & study guides drafted from ATI & lecture material` (written with `&amp;` in HTML).
- `assets/og-image.png` is 1600×840 on a 44px grid. GroupMe draws its link bubble over roughly the top 37% of the image, so the title has to stay below about y=310. If you change the image, bump `og-image.png?v=N` on every page.
- Messaging apps cache previews per URL. To test a change, share a new URL such as `nursingschoolpinkprint.com/?v=2`.

## Content conventions

- Study guides are organized by week (`weekN-study-guide.html`) with mnemonics/memory hooks and quick checks. Material taken straight from lecture slides is tagged as slide content.
- Weekly study guides are built the same way every week. Don't add per-week extras (such as "Connects to earlier units" boxes) unless the owner gives a special note for that week. Links between units belong in the Connecting The Dots guide (`connecting-the-dots.html` at the site root, pinned at the top of the Study guides library via `SITE.connectDots`). It's a full study guide that takes facts from earlier weeks and shows where they apply next (e.g. epinephrine in fight or flight → epinephrine in cardiac arrest); dashed week tags link to the section where each fact was covered. When a new weekly guide is finished, add its connections there too. Every weekly guide carries the same link to it in its header, just above the color key ("See how this connects across units: Connecting The Dots →", `href="../connecting-the-dots.html?upto=N"` with the guide's week); copy it into new guides. `?upto=N` hides everything from later weeks (the "Show connections through" dropdown: All weeks, Week 2… above the key switches weeks or back to All weeks): each table row, list item, quick check, card and box counts as the latest week it links to; pieces with no week link need `data-wk="N"`, and a section or case whose core idea comes from a later week gets `data-min="N"`. When adding content there, give every new piece a week link or a `data-wk`.
- Every study guide's main description (`<p class="lede">` under the title) is exactly: `Drafted from the Week N modules and powerpoints, scaled down for exam crams. Use the mnemonics and memory tricks to lock in lists, then hit the quick checks at the end of each topic.` A short key note may go right under it (`<p class="key-note">`). Never tell students to give material a "lighter review" or to skip it; only pass on what the instructor actually said, such as flagging certain slides as all they need to know for now. Ask the owner before changing this wording.
- Flashcards carry no instructor flags or source tags (no "instructor flagged", "(slides)", "ATI"). The one exception: when sources contradict each other, the card gives each value with a short note naming where it comes from (e.g. "250–450 mL (ATI chapter), 300–400 mL (ATI lesson)"). Study guides explain the same conflicts in side notes, and decks must agree with the guides.
- Spell out every abbreviation the first time it appears on a page, in parentheses: `ADLs (activities of daily living)`. Mnemonics that are already spelled out letter by letter don't need it.
- Content is for adult clients. Leave out infant- and child-focused material (pediatric care, child specimen collection). Keep teen/adolescent content, passing mentions of infants or children, and infant or child rows in a table that covers every age group, so the table stays complete. A child example is fine when it's there to teach the concept being learned (e.g. a 4-year-old bedwetting after a new sibling as an example of regression, a newborn getting maternal antibodies as passive immunity); don't rewrite those as adult cases. The line is focus: the question tests the concept, not child care.
- Every topic quiz is a topic bank that holds as many questions as it takes to cover everything that could be on the exam (sessions draw a random set from it). Unit 1 was rebuilt this way in October 2026 (five topics plus CBC/CMP, which still has its original 40), and Units 2–3 were expanded from 40 per topic to full banks the same month, with a rationale on every option and the full type mix. Keep `count` in `site-data.js` and the card/question counts on each unit `index.html` in sync.
- Unit 1's old Nursing Fundamentals quiz was split into the five Unit 1 topics; its questions keep their `nur114-u1-nursing-fundamentals-NNN` IDs inside the new topics, and `nursing-fundamentals-quiz.html` redirects to the Unit 1 page.
- Quiz questions test the content, not where it came from. Never mark an answer wrong because it is "ATI only" or "not on the checklist"; every wrong option must be wrong on its own merits, and stems, rationales and explanations shouldn't cite the competency, slides, ATI, the instructor, or "what was taught in class". Write every question the way NCLEX or ATI would ("A nurse is caring for a client who…").
- Keep wording plain and accurate. Prefer dropping a forced mnemonic to keeping a confusing one.
- Don't run several labeled items together in one paragraph or table cell ("Gas: cabbage, apples. Laxative effect: dried fruit. Constipating: cheese…"). When a passage has two or more "Label: details" parts, give each its own bullet (`<ul class="tight">`, also inside table cells).
- Never tell students in a guide that something is "not tested" or won't be on the exam; nobody knows what will be. When the owner says an instructor told the class to keep a topic to what's on the slides (or closely related to it), the extra ATI detail can still go in a normal **ATI extra** box, but add `data-quiz="skip"` to that box's `<div>` (invisible to students) and never write quiz questions or flashcards from boxes marked that way. That's rare: five instructors take turns lecturing, each with a different style, so don't carry one lecture's scope note over to other topics or weeks. Week 8 uses it for IV solutions, blood products, acid-base causes and compensation, and the vitamin and mineral food lists: vitamins and minerals are kept simple (know the types and what each does), so never quiz which foods contain a vitamin or mineral. Vitamin K with warfarin is the exception, since it's a medication safety point. Other **ATI extra** boxes can be tested.

## Quiz data

- All quiz questions live in `nursing-study-site/data/nur114/unit-N.json`, one file per unit. Quiz pages hold no questions; they call `loadPracticeQuiz({data, units, topic})` from `practice-quiz.js`. Mix quizzes (`unit-N/mix-quiz.html`, `mix-all-quiz.html`) read the same files, so editing a question in the JSON updates every quiz that uses it.
- Each unit file has `topics` (topic name as shown on the unit page, `slug`, quiz page, `mixLabel` used for the Mix-all results, and `categories` in display order) and `questions`.
- Question IDs are `nur114-u{unit}-{topic-slug}-{NNN}`, e.g. `nur114-u3-safety-001`. **Never change or reuse an ID**, even when rewording a question. A new question gets the next unused number in its topic.
- `category` must match one of the topic's `categories` to show up in the "by category" results.
- Question types: `mc` / `sata` (decided by how many options have `correct: true`), `dragdrop`, `order` (ordered response / prioritizing: list the options in the correct order, no `correct` flags needed, each with a rationale; graded all-or-nothing), and `cloze` (drop-down: a `sentence` with `{1}`, `{2}`… blanks, and options carrying `blank: N` with exactly one correct per blank; graded all-or-nothing). Sessions mix types: about 15% drag-and-drop, 15% SATA (select all that apply), 10% ordered response, 10% drop-down, the rest multiple choice.
- SATA answer counts vary like the real exam: mostly 2–4 correct, a few with all but one, and only rarely one correct or all correct. A question marked `"type": "sata"` stays select-all even with one correct answer. Let the content decide the count: use what the topic really has (e.g. both kidney labs, BUN and creatinine), and never drop a key correct answer or add a correct one the study guide doesn't support just to hit a number. Wrong options must be plausible and wrong on their own merits.
- `data/nur114/exams.json` holds the exam schedule and grading points. `data/nur114/index.json` lists which unit files exist; add a unit there when its JSON is added.
- Quizzes load their data with `fetch`, so test locally with a server (`python3 -m http.server` in `nursing-study-site/`), not by opening the file directly.

## Progress tracking

- The full plan is `design/TRACKING-PLAN.md` in the owner's design zip (with screens). Build in its phase order on the `tracking` branch (preview: https://tracking.nursingschoolprep.pages.dev/) and stop at each check-in. Where the plan conflicts with something already agreed with the owner, keep what was agreed.
- Tracking is on only when the device has a code saved (`js/tracking.js`: code, nickname, weekly goal, study feature switches; localStorage `pinkprint-tracking`). Guests: nothing is saved anywhere, and the site looks exactly as before apart from the locked "My study" box and menu row, and the "Start tracking" banner/button on guest quiz results.
- Progress (answers, mastery, journal, notes, bookmarks) is in `js/progress.js` (localStorage `pinkprint-progress`, keyed by question ID). `?today=YYYY-MM-DD` fakes the date on tracked devices for testing; `?today=off` undoes it.
- Pages: `start-tracking.html` (no Print QR code button; a caption under the QR says it's for phones), `settings.html` (on wide screens Nickname and Weekly goal side by side, equal height, with Your code and devices full width underneath; Switch nickname, Change goal, Show code and the dashboard-name links sit on the right of each heading row (`.se-head`), and while editing, small Cancel / Save buttons take their place there; Switch nickname opens a custom dropdown (the current name plus every free name in a short list that scrolls inside itself) with Reroll; under it, an optional "Name on your dashboard" (`dashName` in synced settings, up to 30 characters, Change / Use my nickname) used only for "Welcome back" on the dashboard, since challenges always use the nickname; the goal picker needs Save, Cancel keeps the old goal; the "Link your phone" QR is hidden when the page is open on a phone), `print-code.html` (QR + code, code passed in the `#` part; no longer linked from Start tracking), `link.html` (device linking, phase 4). Shared page controls in `js/tracking-ui.js`; QR library vendored at `assets/vendor/qrcode.js` (qrcode-generator 1.4.4, MIT).
- Data: `data/wordlist.json` (code words; never remove a word once codes exist), `data/nicknames.json` ("Miss Pinkprint" is reserved and never listed; the owner sets it with `#owner=<phrase>`, checked against `OWNER_HASH` in `js/tracking.js`; type `+` for spaces, or browsers treat the address as a search).
- Quiz pages keep their live layout; with tracking on they add the Bookmark button, "Check · I'm sure" / "Check · I guessed" (Enter / Shift+Enter), the "You were sure" / "You guessed" tag, "+ Add note" above "Next question", the Mastery box and Sure / Lucky guess / Blind spot review tags. Settings switches can turn off the Sure / Guessed tap and notes.
- Today's plan and exam ready (sized for big banks): the student picks a daily size in Settings (10/20/30/40, default 30; `dailySize` in synced settings), done in sets of 10, and any answers that day count toward it. Before the exam ready window the plan is coverage first (`Study.pickPlan`: blind spots → never seen → mistake journal → lucky guesses → bookmarked → review due → still learning → mastered, from the next exam's units) with a pace line ("you'll see about N of M unseen before the window opens"). In the window (3 days before the exam), exam ready = no weak spots left in the exam's units AND a readiness check of 85%+ (`session.html?mode=check`: 40 questions spread evenly over every topic and category, first finish saved via `Tracking.addCheck` to `readinessChecks`, merged between devices; only checks taken in the window count). The old per-question `examReady` records in progress.js are still written but no longer shown. Dashboard, exam plan and Progress show "Seen N of M · K mastered" instead of mastery %.
- Rules: blind spot = latest answer wrong while sure; lucky guess = latest answer right but guessed (still counts toward mastery). Priority (`Progress.STATUS_ORDER`, used by every quiz for tracked students: topic and mix quizzes keep the usual type mix but fill each type's share in this order, and swap in a higher-priority question of another type rather than serve a lower-priority one; guests get the random type-mixed sample): blind spot → never seen → mistake journal → lucky guess → bookmarked → mastered and due for review → still learning → mastered.
- My study (phase 5): `dashboard.html`, `exam.html`, `journal.html` (tabs: Progress (default), Mistakes `?tab=mistakes`, Bookmarks `?tab=bookmarks`; old `progress.html` links redirect there, `#unit-N` opens that unit), `challenges.html` and `session.html` (`?mode=today|examready|weak|journal|bookmarks|blind|review|challenge|group`, plus `unit`/`topic`/`id`). The Journal's middle tab is **Weak spots** (`?tab=mistakes`): blind spots, the Mistake journal and lucky guesses, each tagged. Its one quiz button ("Quiz my weak spots →", between the tabs and the filters, following the Unit/Topic filters; `mode=journal`, old `mode=weak` links too) is `Study.weakSpotsQuiz`: blind spots, then mistakes, then lucky guesses (up to 40); weak spots only, never topped up. The Dashboard has no tiles; its Exam average box has Hide / Show next to the eyebrow, which folds it shut (`gradeHidden` in synced settings) without turning the feature off. Pure rules (dates, coverage (seen) vs mastery, readiness 85/75 with "not enough data" until 20 of the group (or half, if smaller; at least 5) is answered, groups and ranking, today's plan, exam ready, streaks where holiday break weeks (Thanksgiving, after the semester) count only through Settings' "Weekly goals during semester or holiday breaks" (`breaksOff` in settings; on by default): a hit grows the streak and a miss only pauses; turned off, break weeks are skipped, one busy week pass a month, grade points from `exams.json`, the countdown strip) are in `js/study.js`; the pages are drawn by `js/my-study.js`. Their header (`MyStudy.header`) has the site menu at the left (`assets/header.js` in `data-mode="menu"`, loaded after each page's script), the My study links, and Settings then night mode as plain icons at the right. Settings is also in the menu (My study). The current My study tab, and the homepage My study tab, use plum (`--heading`) so they never look like a selected pink filter tab. The homepage shows the countdown strip (follows the Exam countdown switch) and highlights the current unit card (it keeps its Ready / In draft label and still opens its unit page, like the other cards), for tracked visitors only; no mastery bars there.
- Challenges (phase 6): `js/challenges.js` (page + API calls). Each challenge has a 4-character code (like `7KQ2`; the first ones had 8, which still work) that friends type in the "Join with a code" box; short links `/c/<ID>` are redirected by `_worker.js` to `challenges.html?join=<ID>`. Each challenge someone made or joined is saved in their synced settings (`challenges`: id, random ticket, mine/done/gone) and merged between devices by ID. Creating and joining need proof the nickname is yours (claim ticket, or the owner phrase for Miss Pinkprint, saved as `ownerProof` when `#owner=` is used). Topic quizzes show "Challenge a friend" for tracked students with the feature on. Group focus (challenges are for studying together; players are told before starting): once 2+ players finish, the card shows a one-line summary and finishers can open the Group focus page (`challenges.html?focus=<ID>`: weakest topics, most-missed questions with rationales, combined counts only, never who missed what) and "Quiz us on these" (`session.html?mode=group&id=<ID>`). Finishing saves right/wrong per question (`submit_answers` → `challenge_answers`, deleted with the challenge); older pages' `submit_score` still works. Spec: `design/TRACKING-PLAN.md` (additions to the plan in the design zip).
- Class tally (phase 6): `QuizTally` in `practice-quiz.js` sends every answer (guests too) as question ID + right/wrong only, in batches, to `/api/tally/add` → `increment_tally`. The worker drops IDs that aren't in the site's data.
- Stats page (phase 6): `stats.html` (noindex, linked from nowhere). Cloudflare Access (team `pinkprint.cloudflareaccess.com`, app "Pinkprint stats", email one-time code for the owner only) guards `/stats*` and `/api/stats/*` on nursingschoolpinkprint.com. `_worker.js` checks the Access token again (team and AUD constants at the top; not secrets) and calls `class_stats` with the Cloudflare secret `STATS_KEY`, whose hash the owner saves once with `select public.set_stats_key('<key>')` in the SQL Editor. On `*.pages.dev` the page loads but gets no data. Questions show after 5+ answers; warns at 5 or fewer free nicknames.
- Class code (Start tracking): the page shows its steps as a preview, and pressing **Start tracking** pops up the class code (`<dialog>` in `start-tracking.html`, checked with `/api/class/check`) before the new code is made. The server checks it again on the new code's first save (`vault/save` with version 0 must carry `classCode`), so the endpoint can't be called without it. Linking an existing code and saves from existing codes never need it, and the class code isn't kept on the device. It's the Cloudflare secret `CLASS_CODE` (case and spaces ignored); changing it only affects new sign-ups. Unset = no class code asked. Flashcards, quizzes and study guides stay open to everyone.
- Library (shared resources): `library.html` + `js/library.js`, a My study tab (and menu row) for tracked students only. Files live in the R2 bucket bound to Pages as `LIBRARY`; records in `shared_files` (`lib_add`, `lib_list`, `lib_get`, `lib_delete`, `lib_admin_list`, `lib_admin_delete` in `setup.sql`). Every `/api/library/*` call checks the tracking code's lookup on the server; the owner is stored only as a hash and never shown. Uploads: PDF, JPG, PNG, WEBP, HEIC, DOC, DOCX up to 20 MB, type checked from the file's bytes (`sniffFile` in `_worker.js`), title required, units/topics from `SITE.sheets` and the data files ("All" matches every filter), show name or Anonymous, both sharing boxes required, live at once, at most 10 an hour and 30 a day per code. Links can be shared too (Share a: File / Link; `library/addlink` → `lib_add_link`; http(s) only, stored as mime `link`, size 0, with `url` and the site name in `file_name`, nothing in R2; cards show "Open link ↗" in a new tab with `noopener noreferrer`; same sharing boxes and limit). Unit/topic checkboxes swap by themselves (ticking one unticks All; ticking All unticks the rest; none left = All). The Files list starts empty ("Choose a unit" / "Choose a topic" menus, "All units"/"All topics" options) and shows files only after Search. Downloads use short-lived signed links served with `Content-Disposition: attachment`. Preview (pictures and PDFs through `view: true` links served inline, pictures with a sandbox CSP; .docx shown as text by `assets/vendor/mammoth.browser.min.js` (mammoth 1.12.3, BSD-2), loaded only when needed, in a sandboxed `srcdoc` frame; HEIC only where the browser can show it; no preview for old .doc). Uploaders can delete their own files. The owner deletes any file at the unlinked `/library-admin` page with the Cloudflare secret `LIBRARY_ADMIN_KEY`, whose hash is saved once with `select public.set_library_admin_key('<key>')`; nothing on the site hints at it. No `LIBRARY` binding = the Library says it isn't set up.
- Tests: `node tests/progress.test.js`, `node tests/tracking.test.js` and `node tests/study.test.js` from the repo root (Node 18+). Browser checks (`tests/sync/e2e-sync.js`, `tests/sync/e2e-mystudy.js`, `tests/sync/e2e-challenges.js`, `tests/sync/e2e-stats.js`, `tests/sync/e2e-library.js` (start the servers with `CLASS_CODE` and `LIBRARY_ADMIN_KEY` set for this one; the others expect no class code, and `e2e-sync.js` expects empty `vault`/`nickname_claims` tables); `servers.mjs` also stands in for Cloudflare Access) run against `tests/sync/servers.mjs`, a local stand-in for Supabase and Pages backed by a local Postgres with `supabase/setup.sql` loaded.
- Supabase (phase 4): `supabase/setup.sql` creates the tables and the only functions the site may call (run it in the Supabase SQL Editor; safe to re-run). `supabase/test.sql` checks it on a local Postgres. The site reaches Supabase only through `nursing-study-site/_worker.js` (Cloudflare Pages advanced mode; `_routes.json` limits it to `/api/*`), with the URL and publishable key stored as Cloudflare variables `SUPABASE_URL` / `SUPABASE_KEY`, never in the repo. `cloudflare/ping-worker.js` is the separate scheduled keep-alive Worker.
- Sync lives in `js/tracking.js`: PBKDF2 (600,000 rounds, separate salts) turns the code into a lookup ID and an AES-GCM key; progress, notes, nickname and settings are encrypted in the browser; saves use a version number and merge per question (newest change wins). Linking: `link.html` (typed code or QR `#code=`), Settings, and "Already have a code?" on Start tracking. Delete my data removes the saved copy, frees the nickname and clears the device; other devices clear on their next sync.
- `tests/sync/` is a two-device end-to-end test against a local Postgres running `setup.sql` (see the notes at the top of `servers.mjs`).
